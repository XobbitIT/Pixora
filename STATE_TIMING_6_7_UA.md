# Pixora — збереження стану та облік часу, завдання 6–7

База: `1.0.14-rc.8+local-evidence-3b`. Нова збірка: `1.0.14-rc.8+local-state-timing-6-7`, 19.10.2026.

## Результат етапу

Реалізовано контроль власника конфігурації й застарілих фонових результатів; розділено часові фази й вкладені витрати вводу. Додатково проаналізовано два надані звичайні Standard-запуски та відео. Зміни команд малювання, прискорення або геометричної компенсації в цій збірці немає.

## Завдання 6: конфігурація та профілі

**Проблема.** Старий ConfigHistory журналював ревізії та зберігав пропущені маски в архіві, але дозволяв будь-якій копії Settings перезаписати актуальний файл. Це захищало частину raw evidence від повного знищення, проте не запобігало поверненню застарілих координат, параметрів і активних профілів.

**Новий контракт.** Після Load або успішного Save об'єкт отримує непублічний immutable stamp: абсолютний шлях, ревізію та SHA256 точних байтів. Clone переносить значення stamp, а не спільний змінний об'єкт. Перед збереженням ConfigHistory перевіряє, що stamp збігається з поточним файлом. Зміна байтів навіть без зміни revision, видалення раніше завантаженого файла або новий об'єкт без права на існуючий файл спричиняють конфлікт до заміни. Новішу копію збережено. Єдиний writer використовує внутрішній gate і окремий exclusive file lease для співпрацюючих процесів.

MainWindow є власником публікації. Рухове калібрування тепер працює з відокремленою копією; Dispatcher публікує її лише якщо незмінні поточний об'єкт і його content identity. Перевіряються як заміна owner, так і редагування JSON у тому самому об'єкті. Після публікації наступна фонова операція знову отримує окрему копію. Скасований або застарілий результат не підміняє UI/config.

При файловому конфлікті показується локалізоване пояснення й START блокується до перезавантаження актуального стану або явного імпорту. Автоматичного злиття довільних старих і нових полів немає.

**Імпорт і міграція.** Формат config лишається schema 3: owner stamp у JSON не записується. Старі ключі мігрують тим самим шляхом. Явний імпорт — окрема операція з expected hash, зафіксованим до відкриття діалогу. Він може замінити пошкоджений файл, але не підміняє звичайний Save. Raw оригінал зберігається в content-addressed history; зміна target поки відкрито діалог відхиляє імпорт.

**Стани та продовження.** Якщо маска є лише в архіві/несумісному контексті, UI показує «Застаріло», а не «Не виміряно». Новий Rejected не маскується старим архівом і не дозволяє фарбування. Збережено окремий стан відсутності ядра. RESUME пояснює різницю формату identity, інший план, неправильну позицію або неузгоджений лічильник. Правила прийняття checkpoint, PlanIdentity і право нового START замінити попередній прогрес не змінені.

## Завдання 7: час і ввід

**Взаємовиключні фази:** `Colors + Motion + Service + Finish + Pause + Countdown = Wall`. Finish тепер окремий; він входить до Active, але не до Service. Active як і раніше `Wall − Pause − Countdown`. UI показує завершення окремо. Журнал має revision `exclusive-phase-v2-finish-separated`; run.json — revision 4, щоб нову семантику не змішували зі старим Service.

**Вкладені метрики run.json:** рухові пакети/точки й час рухового шляху; requested/actual wait та кількість викликів; safety/editor/tool checks; фактичні читання курсора guard із кількістю помилок; усі mouse/keyboard SendInput API calls поточного Run-worker, запитані й прийняті події та partial/failed calls. Облік SendInput має thread-local scope і відновлює попередній scope після виходу. Інші потоки не включаються в цей worker.

Старий `SendInputSeconds` збережено як час усього рухового шляху, включно з упаковкою. Новий `NativeSend.Seconds` окремо вимірює системні SendInput API calls. `GuardCursor` рахує читання tracked path, endpoint і paint-down; це не обіцянка обліку всіх курсорних читань у захопленні чи старих діагностичних шляхах.

Ці метрики **не додаються** до фаз Wall: наприклад, actual wait включає вкладену safety/editor/cursor роботу. Вкладені метрики та межі scope прямо описано в JSON. У snapshot додається актуальний `remainingEstimate` на active-clock, без повторного додавання паузи/відліку. Після resume він читається з поточної моделі й актуального прогресу; фіктивні завершені операції не створюються. Алгоритм прогнозу не переналаштовувався.

Команди, обраний емітер, перевірки, threshold і requested waits збережено. Сам облік має малу обчислювальну вартість; його не оголошено безкоштовним або доказом прискорення.

## Що показали нові матеріали

86/86 та 84/84 Standard-операцій завершено. У вибраних native ділянках фінальних вертикалей max залишку краю від прямої близько 0,08–0,10 px. Це локально рівні контури, але ширина й абсолютне положення ще не збігаються з простою моделлю команд.

У відео знайдено проміжний стан чорної смуги: середня ширина 72,123 px до сусідніх білих проходів і 61,484 px після них. Видимий перезапис краю білим — сильний напрям для наступної моделі меж. Це вимір зі стисненого відео, не незалежний сертифікований stroke-profile. Підстави для універсального зсуву 6 px немає.

Два завершені run.json попередньої збірки мають актуальні лічильники й timestamps. У 29 записах нової історії config конкретного мовчазного стирання масок не виявлено. Новий захист реалізовано за відтворюваним дефектом коду, а не за вигаданою причиною цього тесту. Повний окремий аналіз: `Pixora_Live_20261019_2256_Analysis_UA.md`.

## Перевірка та відтворення

- **626 Core / 204 WPF PASS**, включно з 84-layout DPI-матрицею; Core і App build — **0 warnings / 0 errors**.
- Приріст проти Evidence 3b:11 Core cases та 6 WPF cases. Перевірено stale clone, зовнішні зміни без revision bump, видалення файла, одночасних власників, file lease, явний імпорт/корупцію/міграцію, archived/rejected стани, точні причини RESUME, відокремлену UI-публікацію та скасування.
- Перевірено finish/pause/countdown без подвійного обліку; реальну кількість callback читань та їх винятки; ізоляцію й partial counts SendInput-meter без системного вводу; schema4 та clock semantics snapshot.
- Stress 50 save/load тепер продовжує об'єкт, прочитаний на попередньому кроці. Небезпечне збереження 50 нових неавторизованих owner у той самий файл замінено окремими тестами явного import і stale-rejection.
- Replay8 історичних планів проти Target 1: target, identities, команди, requested waits та frozen emitter events ідентичні. Load stamps не потрапляють у serialized settings/PlanIdentity. Фактичний слід цей replay не моделює.
- Для focused WPF: `OUTPUT --settings-owner-only` та `OUTPUT --input-timing-only`. У тестовому host системний ввід заборонено. NuGet network audit у цьому офлайн-прогоні не виконувався.

Пакет доказів містить source/tests, логи фінальних перевірок, replay, Snapshot203 файлів і скрипти аналізу. Відео не дублюється в ZIP, збережено його шлях/SHA та витягнуті кадри. Поточний код не видається за вже перевірений у Rust: надані користувацькі запуски належать попередній Evidence 3b.

## Наступний етап

Модель меж і накладання рухомого пензля: порівняти black-only та after-white у native кадрах, розділити позицію/напрямок/пакети й перевірити модель на незалежних даних. Збирач 42 проби залишається в пакеті через `Collect_Standard_Evidence.cmd`. До узгодженої моделі жодних довільних коефіцієнтів чи послаблення RGB12/contrast80 не внесено.

## що НЕ доведено

Готовність фізичної якості всіх зображень Standard, універсальна причина відхилень меж, придатність Adaptive, живий успіх нових owner/timing шляхів або приріст швидкості. File lease серіалізує співпрацюючі writer; він не робить публічний JsonObject загалом thread-safe й не контролює довільні сторонні редактори файлів. Метрики scope обмежені worker/guard шляхами. Повного 42-пробного native набору в наданому тесті немає.
