# Відповідь на відгук Qoder: Standard Native Line

Історичний звіт етапу reviewfix (v2). Поточна реалізація діагностики та endpoint guard v3 описана у `STANDARD_LINE_LAB_UA.md`.

Дата:17.10.2026. Робоча мітка `1.0.14-rc.8+local-standard-line-reviewfix`, емітер `standard-native-shift-line-v2`. Прототип OFF за замовчуванням, фізична якість не сертифікована, нових малювань від користувача не запитано. Прочитано переданий відгук Qoder; агентам повідомлення не надсилалися.

## Результат звірки

Qoder підтвердив цілісність попереднього пакета, співвідношення DLL, арифметику та вміст логів. Не називаємо це другим виконанням C# чи живою перевіркою. Нові реплеї нижче виконав Codex.

### 3.1: точна межа OFF-сумісності

OFF зберігає target, семантичну ідентичність плану, schedule та номінальну послідовність вводу Quality1. Це не твердження про весь runtime. Очищення непідтвердженого `motion_transport_rate` свідомо змінює ETA з імпортованим snapshot і з OFF. Приймаю уточнення формулювання.

### 3.2: замкнений ланцюг RC8 → Quality1 → поточний OFF

Одні й ті самі1020 записаних операцій відтворено трьома DLL, без повторної побудови покриття. У всіх:31521 точка при утримуваній кнопці, нуль порушень осі/кінців,27 вертикалей по470px.

- `commandsSha256`: `2E5A7F03142CAC32E03D7B26B38D8F6AD5B0CE2FA7AF5700960911C87B449FEB`.
- `emittedSequenceSha256`: `5125FF0B600276365E915F5AED3A55EE40377F8609B34A3DC38B83EF8AF0C5A1`.

Другий хеш охоплює порядок операцій, пакети Move з усіма точками, Button/Shift і точні значення Wait. Ідентичність підтверджена на записувальному fake; вона не доводить фактичної доставки Windows або рендерингу Rust. Входи, код і три результати Bridge включені до пакета.

### 3.3: повний replay і ціна гіпотези

Для кожного рядка ON/OFF зберігають target і геометрію schedule. Колірна палітра й геометрія взяті зі snapshot останнього запуску:Canvas917×919,DPI96,Rust Palette,Stable,затримка20мс; cell/speed явно зазначені. Це конкретні сценарії, не універсальна ціна для всіх пристроїв.

| Сценарій | Операцій | OFF: запитані очікування,с | ON: запитані очікування,с | Зміна |

| Заморожені команди запису,cell8 Max Speed |1020|69.4521|122.4000|+76.24%|
| Той самий повний source,поточний dense planner,cell8 Max Speed |2716|184.9311|325.9200|+76.24%|
| Test_01,cell2 Rapid |1288|228.3484|154.5600|−32.31%|
| Test_02,cell2 Rapid |2769|259.5638|332.2800|+28.01%|

1020 — заморожений історичний schedule, не результат поточного dense planner. 2716 — нова побудова того самого source/settings. Test_02 у цій таблиці не оголошується тотожним старому2745-командному запуску: використано явно збережений case input зі snapshot останнього запуску, а рівність усіх параметрів того старого сценарію тут не перевірялась. Початковий короткий72-командний replay не підміняє ці повні сценарії.

Дані містять також length buckets, кількість Move/Shift, прогноз Active окремо від countdown та число точкових перевірок preflight. Гібрид за довжиною не вмикаємо: вигідна модель часу не доводить відповідної якості чи однакового відбитка.

### 3.4: ETA та preflight

Номінальні очікування — це значення, запитані в fake, а не фактичний час. Наприклад, для1020-командного сценарію холодна модель Active становить77.4621с OFF і130.4100с ON; до неї додається окремий countdown. Ці числа включають евристичний службовий час, але не виміряну вартість Win32 preflight/планувальника ОС/рендерера.

Для ON на цих1020 командах preflight має95217 точкових перевірок чужого вікна. WindowAt усередині містить WindowFromPoint/GetAncestor, окремо читається foreground. Це не95217 виміряних секунд чи одиничних системних викликів. Середній runtime residual після навчання може поглинути частину preflight; окремої моделі ціни на довжину поки немає.

Вікно між preflight і вводом зберігається. Наступні Move/Button перевіряються повторно. Перевірка заданого маршруту не доводить відсутності прихованого з'єднання, якщо Rust має іншу семантику Shift: цей ризик лишається живим блокером.

## Виправлення коду

1. `StandardLineMotion.Enabled/Applies` відсікають Experimental/невідомий input engine та затримку нижче20мс. Прямий виклик Draw у такому контексті відмовляє до вводу. Це обмеження області прототипу, а не підтвердження достатності20мс при низькому FPS. Revision v2 відокремлює його від v1.
2. Чуже вікно всередині Native Line має окремий `pauseReason=foreign_window_on_route`; геометрія/no-go лишаються `coordinate_out_of_bounds`. Обидва шляхи відпускають ввід і переривають виконання.
3. Standard evidence відмовляє для порожньої або багатосегментної операції до створення файла. Перший сегмент більше не може тихо представляти весь batch. Поточний planner Standard і так дає один сегмент.

## Відкриті питання живої перевірки

- Shift до mouse-down: джерело Facepunch не доводить відсутності зв'язку з попереднім штрихом для нашої послідовності. Порядок навмання не міняв.
-20мс — запитана затримка, не спостережений ігровий кадр. Не вводив довільні «безпечні»27/40мс за старим Size1. Мінімальний інтервал треба встановити окремо.
- Геометрія, кінці, товщина, AA/opacity штатної лінії не кваліфіковані. Переносити докази старого вільного штриха на новий метод не можна.
- У поточному Standard лише круглий Size3. Інші Size/Shape не заявляються цим прототипом; їхня майбутня матриця не є умовою перевірки саме цього обмеженого шляху.
- Sticky Keys — неперевірений системний ризик. Налаштування Windows не змінювались; відсутність діалогу не припускається за старими короткими Shift-тестами.

Підготовлено machine-readable план двох несуміжних вертикалей із прозорим коридором: спершу виявляється зайве з'єднання, а не малюється повна картинка. Варіант B (Shift після mouse-down) описано як майбутнє порівняння; у runtime його не реалізовано. ±0px стосується команди/прочитаного системного курсора. Фізичні caps та зміщення відбитка оцінюються окремо, без підміни їх нульовим зміщенням курсора.

Пауза/Alt+Tab не повертаються у звичайне ручне завдання користувачу. Новий Shift-контракт потребує власної контрольованої перевірки, коли буде можливість її виконати. Зараз жоден живий прогін не виконано.

Прототип лишається OFF, RGB12/contrast80/геометричні guards не послаблені, Adaptive не змінено. Старі ZIP збережені, commit/push не виконувались.

## Перевірки цього продовження

585 Core-тестів і172 WPF-сценарії, включно з84-layout DPI matrix, пройшли. Обидві збірки мають0warnings/0errors. Новий Core-тест відсікає небажаний input engine/короткий інтервал; новий App-сценарій відхиляє непідтримувані batches. Наявний guard-тест тепер перевіряє окрему причину чужого вікна. Тестовий хост блокує SendInput; Pixora.exe і Rust агент не запускав, живого вводу не виконував.
