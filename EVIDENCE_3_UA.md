# Pixora Standard Evidence 3 — реалізація завдання 3

Дата: 19.10.2026. База: `1.0.14-rc.8+local-target-1`. Нова збірка: `1.0.14-rc.8+local-evidence-3`.

## Результат

Реалізовано окремий службовий збирач одного запуску. Він не викликається звичайним START і не змінює його емітер/маршрути/затримки. Живого запуску агент не робив. Інструкція до погодження — `EVIDENCE_3_LIVE_SCENARIO_UA.md`, сім кроків.

Протокол `standard-evidence-series-v3` містить **38 проб / 40 кольорових фаз / 212 штрихів**:

- 36 одиничних: H/V × прямий/зворотний × 16/64/400 px × 3 блоки. Порядок усередині блоків перемішаний із зафіксованим seed; проби займають різні рознесені ділянки.
- Дві додаткові складені проби H/V: 72 сусідні чорні проходи, потім по 8 білих з обох боків. Є окремі lossless before/after для чорної та білої фази. Це дозволяє побачити слід до перекриття білим, якого бракує в старих strip-запусках.

Для одиничних проб є native before/after кожного штриха. Для двох складених смуг кадри зберігаються після кожного кольору, а не після всіх 88 окремих ліній; кожна така лінія має власну повну gzip-трасу. Це явно записано в context, без видавання групового кадру за знімок кожного штриха.

## Реалізація

`StandardEvidenceSeries` відділяє геометрію експерименту від вікна та UI. Усі координати фізичні, без нових DPI-множників/offset/scale. Мінімальний Canvas — 900×920; останній користувацький 1044×1043 підходить. Початкове виділення не обрізається. Ділянки проб не перетинаються, запас спостереження — 10 px, і жодна команда не виходить за задану область. Запас є межею резервування експерименту, не сертифікованим Possible footprint.

Очищення/Undo не автоматизовано: потрібне одне окреме чисте полотно на старті. Перед кожною пробою її ділянка порівнюється з початковим baseline за RGB12. Після кольорової фази фіксуються зміни поза резервом. У разі порушення серія INCOMPLETE, збережені файли лишаються. Ці перевірки не доводять, що початкове полотно порожнє — це передумова користувача.

`EvidenceSeriesTraceInput` передає виклики в поточний dense guard v3, зберігаючи endpoint/tool/focus guards. **Один реальний пункт на пакет**, GetCursorPos після send і наявного wait; QPC початку/кінця читання, команда, фактичний курсор, помилка API/Win32Error. Проміжні координати з великих пакетів не вигадуються. Читання одразу після send може передувати підтвердженню транспорту; таке значення не підмінюється командою. Реальне завершення контролює існуючий guard.

Профіль навмисно **Rapid timing / Pitch1 / Batch1 / frame20ms / round Size3**, а не звичайний Max Speed. Витрати GetCursorPos і запису змінюють часовий контекст. Це записано в manifest/context/трасах, performanceQualified=false. Старі v1/v2 quality/direction pilots лишаються замороженими й не перейменовуються на новий протокол.

`StandardEvidenceSeriesRunner` зберігає append-only події після кожного штриха, фаз і проб; поточний статус замінюється атомарно. Trace flush виконується після відпускання кнопки. У разі помилки дані попередніх проб і часткова траса поточної лишаються. `started.json` створюється через CreateNew; повторного виконання, retry чи resume для тієї самої серії немає. Наявний checkpoint звичайного малювання не використовується. Стан DATA_COLLECTED означає комплектність запису, а не правильний RGB/покриття чи physical PASS.

CLI доступний лише явним прапорцем:

```
Pixora.exe --standard-evidence-series init NEW_DIRECTORY
Pixora.exe --standard-evidence-series run NEW_DIRECTORY
Pixora.exe --standard-evidence-series collect PARENT_DIRECTORY
```

Init не надсилає native input і не зберігає імпорт назад у користувацькі налаштування. Collect створює новий каталог із timestamp/id, заморожує settings/protocol і SHA App/Core та запускає серію після 10-секундного відліку. Перед вводом Rust має вже бути foreground; фокус не захоплюється автоматично. ReadSeries відхиляє змінені файли/бінарний контекст. Focus/F6/ESC/tool/API failure → відпускання вводу та INCOMPLETE. Звичайні кнопки малювання не запускають цей шлях.

У збереженому target 522×522 вже є **324 клітинки #807FFF + 83 клітинки #3333FF = 407**. Є і відповідні кольорові команди. Отже, додаткові відтінки присутні до введення; це не доказ помилкового вибору фарби. Положення/форма їхнього фізичного сліду потребують окремого зіставлення. Додано `Intake/target-extra-colours.png` та JSON. Автоматичного видалення цих кольорів чи зміни image recipe не додано.

У відгуку Qoder прийнято виправлення Y: попереднє 1.0021 ґрунтувалося на помилково вибраних рядках рамки; прямий observed/command ≈0.998 підтверджений рецензентом на правильних межах. Коефіцієнт у продукт не внесено. Два однакові профілі V-strip рахуються як один ефективний сценарій. Їхня тотожність не доводить універсальну детермінованість Rust або всіх планів.

Запит Qoder на target 18.10 у dense-режимі новий тризуб не закриває: інший target не є контрольованою парою. Повтор великого малюнка зараз не запитується. Поточний інструмент збирає бракуючі кадри між кольорами одним діагностичним запуском після погодження інструкції.

## Офлайн-верифікація

- Фінальні збірки Core/App — **0 warnings / 0 errors**.
- **614 Core PASS / 192 WPF PASS**, включно з 84-layout DPI matrix.
- П’ять нових Core-випадків: повнота протоколу, рознесення/межі та rebasing, незмінність seed/протоколу, RGB12/13 і забруднення резервів, поточний dense emitter/поодинокі move та release при відмові.
- П’ять нових App-випадків: фактичні per-command readings і QPC, focus/tool/F6/API error із release і сирими записами, незмінність init, один повний fake-прогін та часткові відмови без стирання/повтору.
- Повний записувальний fake виконав **38 проб, 40 фаз, 212 штрихів**, зняв кадри між кольорами й зберіг 212 трас. Усі fake-capture metadata позначені synthetic=true/nativeInput=false. Це не жива кваліфікація.
- Вісім історичних планів і заморожений емітер порівняно з Target 1: target, execution identity, маршрути та задані очікування збіглися. Вводу у Rust не надсилалося.

В одному з проміжних повних прогонів стався UnauthorizedAccessException під час файлового запису: серія стала INCOMPLETE на 37/38 пробах, 39/40 фазах і 196/212 штрихах, а попередні файли збереглися. Причину разової відмови доступу не встановлено; її не названо помилкою пензля. Додано повний stack/HResult у події відмови. Наступний окремий fake-прогін записав усі 212 трас; фінальний повний повтор пройшов усі 192 WPF-випадки, включно з повним 38/40/212 збором. Автоматичного повторення paint після I/O-помилки немає.

Архів містить Source/tests, командний replay з входами, журнали, manifest SHA, snapshot нового матеріалу та synthetic run. Receipt містить SHA бінарних файлів і список відмінностей від Target 1. Архів перевірений за всіма payload SHA. Коміт/push не виконано.

## що НЕ доведено

- Збирач ще не запускали живцем. Доступність цих резервів, стабільність screenshot-порівнянь і фактичний час у Rust офлайн не підтверджені.
- Фізична нерівність ліній/неправильна ширина не виправлені цією ітерацією. Це реалізація бракуючого інструмента завдання 3; нових припущених масштабів, радіусів чи ослаблення RGB12/contrast80 немає.
- 36 проб не є B0-оцінкою шуму в одній координаті чи затвердженим train/held-out для production mapping. Різні позиції та час тут не розділені причинно.
- Результат Rapid/Pitch1/Batch1 не кваліфікує Max Speed/великі пакети, Adaptive, інші Size або форми. Потрібна відповідність повного контексту.
- Фото й записи завершення не є піксельним сертифікатом кольору/покриття. `inGameTest=false`, `physicalQualityCertified=false` для нової збірки.
