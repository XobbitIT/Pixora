# Pixora Standard Direction 1 — реалізація

Дата: 18.10.2026. Збірка: `1.0.14-rc.8+local-standard-direction-1`.
База: Standard Stability 1; враховано повторну перевірку відгуків від 18.10.

## 1. Поточний стан запуску

Раніше довгий запуск на паузі залишав `last-run/<id>/run.json` у початковому `outcome=preparing` з нульовим прогресом. Тепер діагностичний файл має revision 2 та записується:

- після START перед налаштуванням пензля — `running`;
- після кожних 50 завершених операцій і на кінці групи;
- після відпускання вводу й початку паузи — `paused`; під час очікування оновлюється приблизно раз на секунду;
- після успішної перевірки редактора при продовженні — `running`;
- при завершенні/скасуванні/помилці — відповідний terminal outcome.

Додано `done`, `total`, `group`, `line`, `pauseReason`, `checkpointOwned`, `sequence`, `updatedUtc`. Збережено старі поля identity/targetIdentity, times, sourceAvailable, snapshotComplete і problem. Запис атомарний: тимчасовий файл у тій самій папці та перейменування, щоб читачі не отримували обрізаний JSON.

Це окремий статус діагностики. Він **не бере ownership checkpoint і не записує resume-v3.json**. Новий START без першого штриха не замінює старий прогрес. Запис під час малювання виконується після повернення зі штриха; під час паузи ввід уже відпущено. Частоту щосекундного оновлення не додано всередину виконання штриха.

## 2. Окремий протокол перевірки напрямків

Додано `standard-direction-experiment-v2`, відокремлений від попереднього `standard-quality-experiment-v1`:

**1 центральна позиція × 2 осі × 2 напрямки × 2 пресети × 3 блоки = 24 обов’язкові samples.**

- одиночні H і V довжиною 400 фізичних px;
- прямий і зворотний напрямки;
- Safe (Pitch1/Batch1) і Max Speed (Pitch3/Batch16);
- Size3 round, frame20ms, identity mapping;
- порядок усередині кожного блоку перемішано до збору, seed=18102027;
- мінімальне виділення 660×660; вибране користувачем полотно не змінюється;
- перший чистий Canvas — передумова оператора; перед кожним наступним sample потрібен чистий стан, який порівнюється з native baseline першого sample;
- автоматичних Undo, очищення, пропуску невдалих sample, повтору чи resume немає.

Центральна позиція потрібна для невеликого розділювального пілоту. Це **не сітка mapping, не B0 і не заміна held-out сертифікації**. Попередня 60-sample серія H/V × суцільний/сегментований × 5 позицій залишається доступною під своїм CLI й revision. Старі набори не перейменовуються у v2. Інші assembly hashes роблять стару розпочату серію несумісною з новим виконуваним файлом — для нового коду створюється нова папка.

## 3. Що саме записується про курсор

Обгортка емітера зберігає список команд кожного пакета, час до та після виклику, запитане очікування, фази held/wait/released і фактичний системний курсор.

- У Safe пакет має одну точку: є спостереження після кожної окремої команди.
- У Max Speed збережено справжні пакети до 16 точок. Є весь список команд, але курсор спостерігається **лише після пакета**. Це явно позначено `cursorScope=packet end only`; покрокової фактичної траси всередині пакета не заявлено.
- Помилка читання зберігається як `CursorReadSucceeded=false`, `Cursor=null`, а не успішна координата (0,0).
- Невідповідність кінцевої команди й курсора або помилка API переривають sample; зовнішній finally відпускає ввід. Відмова до paint-down не дозволяє його виконати.

`Seconds` і `StartedSeconds` — монотонний Stopwatch Painter, а не час обробки події всередині Rust. Читання API та запис діагностики можуть впливати на реальний темп. Збереження запитаних пауз і пакетів не є доказом незмінного wall time або швидкодії Max Speed без інструментування.

## 4. Час guard усередині Wait

В явному direction-пілоті додано opt-in лічильник кількості й сумарного часу guard-викликів **усередині** `InputDelay.Wait`. Статистика запиту/фактичного часу зберігається окремо на кожен штрих.

Тривалість guard вкладена в actual wait. Її не треба додавати до загального часу повторно. Різниця actual-requested залишається змішаною величиною: API, планувальник, guard та інша робота. Новий лічильник не називається «чистою затримкою таймера» й не дає дозволу прибрати перевірки. У звичайному START цей додатковий облік вимкнено.

## 5. Запуск внутрішнього пілоту

Це інструмент розробника, без нових кнопок у звичайному UI. START автоматично його не виконує.

Закрити інші копії Pixora. Після звичайного захоплення й підготовки редактора:

```text
Pixora.exe --standard-direction-evidence init C:\Evidence\direction-new-series
Pixora.exe --standard-direction-evidence sample C:\Evidence\direction-new-series 0
```

Далі індекси 1…23 у зафіксованому порядку. Кожен sample — окремий запуск після ручного очищення полотна. Є 5 секунд, щоб повернутись у вже відкритий Rust; програма не забирає фокус, не відкриває редактор і не очищає Canvas. Старі папки sample не перезаписуються.

`init` читає canonical config або legacy config без імпорту в користувацьку папку; Standard-пресет застосовується до копії. Фіксуються protocol/settings/App/Core hashes. Відсутній обов’язковий попередній receipt або зміна контексту блокують новий ввід. Помилка дає INCOMPLETE; всі 24 зібрані samples означають DATA_COLLECTED, не фізичний PASS.

Зберігаються native background/before/after, пара на кожен штрих, cursor JSON, context, receipt і стан серії. Перший baseline порівнюється за незмінним RGB12, метрики лінії використовують незмінний діагностичний before-after delta>80. Вони не є новим контрактом кольору чи готовою компенсацією координат.
