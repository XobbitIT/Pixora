# Pixora 1.0.14-beta.46 — буфер обміну та діагностика повзунків

Жива діагностика ноутбука beta.45 відокремила дві помилки. HEX вставляється, але копіювання іноді завершується порожнім буфером приблизно через 1,14–1,17 с. У наступній перевірці Size число 1.00 читається правильно, але смуга не розпізнається. Interval у цій сесії не перевірений: виконання зупиняється раніше.

## Виправлення

- Вікно-власник буфера тепер створюється в окремому STA-потоці з Dispatcher.Run. Потік вводу може чекати кадри та опитувати копіювання, а вікно продовжує обробляти повідомлення Windows. Раніше воно створювалося в робочому потоці без власного циклу повідомлень. Це дефект коду, але поки не доказ, що саме він спричинив усі очищення на ноутбуці.
- WM_DESTROYCLIPBOARD / WM_RENDERFORMAT / WM_RENDERALLFORMATS записуються в чергу й потім у `clipboard_capture` із часом повідомлення. Обробник вікна не пише файли й не читає буфер. `owner_created` показує окремі потоки вводу та власника. PID автора EmptyClipboard цим способом не визначається.
- Проміжне очищення під час активного читання більше не завершує очікування копіювання. `copy_empty_pending` залишає старий підтверджений sequence: наступний текст можна прочитати, але порожній незавершений результат не дозволяє новий запис або відновлення поверх сторонньої зміни. Невідомі пізні дані перед записом все ще блокуються.
- При відхиленні смуги зберігається саме проаналізований знімок `slider.png` та `diagnosis.json` у `%LOCALAPPDATA%\Pixora\controls-diagnostics`. Журнал `slider_read_failed` містить шлях, DPI, межі захоплення і причини: обрізана смуга, висота, частка числового поля, розірване заповнення, кілька смуг або відсутність зеленої смуги. Критерії розпізнавання не послаблені.

## Перевірки та межі

346 Core / 107 WPF: старі реальні slider fixtures, причини відхилення без зміни прийнятої геометрії, збереження знімка, відповідь службового вікна при заблокованому потоці вводу, проміжне очищення → текст, незавершене очищення → заборона перезапису, попередні тести конфліктів і відновлення. Ізольований Windows CI також перевіряє справжнє копіювання з іншого потоку та відновлення буфера.

Затримки beta.45, точний HEX/numeric match, модель пензля, контраст 80, RGB tolerance 12, Speed Probe, planner та аудит збережені. Size 1 не оголошений відкаліброваним. Причина конкретного `slider_check.actual=null` потребує нового знімка. Новий живий тест ноутбука потрібний перед висновком про виправлення Rust HEX.

Microsoft документує повідомлення попередньому власнику при очищенні буфера: [Clipboard Operations](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-operations). Потоки з вікнами мають обробляти повідомлення: [Messages and Message Queues](https://learn.microsoft.com/en-us/windows/win32/winmsg/about-messages-and-message-queues).
