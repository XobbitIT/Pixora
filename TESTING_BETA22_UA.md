# Pixora beta.22 — перевірка виправлень відеотесту

Закрий попередню Pixora, розпакуй весь архів в окрему папку й запусти Pixora.exe. Перевір beta.22 у шапці. Потрібен .NET 8 Desktop Runtime x64. Старий RESUME не використовуй: контекст Speed Probe та ідентифікатор плану змінилися.

Калібрування діаметрів пензля збережене, якщо форма, полотно та захоплення не змінилися. Просторове калібрування й Speed Probe треба виконати заново. Старі результати діагностики залишаються доступними, але не стають підтвердженими маршрутами нової версії.

## 1. Палітра й HEX

1. У Rust відкрий звичайну палітру, у Pixora вибери «Палітра Rust». Перевір Size / Interval / Opacity та калібрування пензля.
2. Для HEX відкрий HEX-палітру у грі, вибери HEX Direct у Pixora та використовуй окреме захоплення HEX-controls. Перевір кольори FF3333, 12AC5F, 0397E2.
3. Навмисно залиш невідповідний режим: Pixora має зупинитися перед зміною пензля й показати пораду переключити палітру або повторити захоплення. Якщо інший layout не захоплений або не підтверджений трьома доріжками, повідомлення лише просить перевірити поточний режим; воно не вгадує його.

## 2. Просторове калібрування → Speed Probe

1. Очисти полотно. Вибери Size 3 та «Виміряти просторові зміщення».
2. Потрібні шість повністю підтверджених контролів. У діагностиці пропуски = 0, невпевнені = 0. Часткове покриття не вважається успіхом.
3. Очисти полотно знову. Запусти Speed Probe; не рухай мишу й не перемикай вікна.
4. Обидва незалежні повільні контролі мають пройти. Проміжне зміщення, наприклад −1 px всередині заздалегідь виміряного діапазону −4…0, більше не відхиляється лише через відсутність у трьох точних вибірках. Зміщення за межами діапазону або прогалина залишаються відмовою.
5. Далі мають з’явитися етапи звичайного руху й Shift. Кандидати 32 / 20 / 12 / 8 мс, три повторення і перевірка із запасом залишилися. Невдалий кандидат не є підтвердженим маршрутом.
6. Повтори для потрібних Size 1 / 10 / 20. Якщо не вистачає місця для чистих ділянок, програма має пояснити обмеження — не обходь його нанесенням проб поверх попередніх.
7. Окремо перевір F6 та втрату фокусу: причини переривання тепер різні в повідомленні й журналі. Перед повтором очисти полотно.

## 3. Швидкість звичайного перенесення

1. Для порівняння з відео використай те саме зображення чотирьох блоків, те саме полотно, форму пензля, деталізацію й палітру. Спочатку вимкни «Використовувати підтверджений маршрут» та аудит; залиш Experimental 12 мс, packet 16 і попередні налаштування adaptive/fast.
2. Виконай новий START до 100%. Запиши початковий прогноз, час на 25 / 50 / 75%, кінцевий час та результат. Референс beta.21: 150 операцій, 132.56 с активного часу, з них 112.32 с руху. Порівняння має сенс лише за однакового плану й приблизно однакових умов гри.
3. Після завершення у Pixora має бути фактична тривалість. Позначка 100% без аудиту означає виконані команди, а не доказ покриття.
4. Перевір суцільність усіх квадратів, краї, правильність кольорів та відсутність сторонніх ліній. Полотно перед START має бути чистим від Speed Probe.
5. Перевір зупинку ESC, F6 → повернення у Rust → F6 та STOP → RESUME до завершення. На паузі пензель не має залишатися натиснутим, пауза не входить в активний час.
6. Лише після підтвердженого Speed Probe увімкни виміряний маршрут та повтори новий START. Тести 8 мс не вважаються стабільними лише за швидшим проходженням лічильника.

## 4. Вікно й курсор

Після успішного малювання Pixora за замовчуванням лишається згорнутою: Rust має бути видимий, курсор — біля останньої дії на полотні. Відкрий Pixora вручну й перевір кінцевий час. У «Налаштування → Автоматизація» увімкни «Показувати Pixora після завершення малювання» й повтори короткий запуск: тоді вікно має повернутися. При помилці або скасуванні вікно повертається для пояснення стану.

## 5. Аудит і локалізація

На простому контрастному зображенні окремо увімкни аудит. Перевір діагностику, пропуски, невпевнені пікселі та можливе дофарбування. Перемкни українську / англійську: нова опція вікна, причини відмови й кінцевий час мають бути перекладені. Порівняння HEX 64 / 96 / 128 / 256 тепер показує різницю відносно 256; час там залишається прогнозом.

## Що записати для аналізу

- Відео: налаштування, калібрування, весь запуск, фінальний результат та кінцевий час у Pixora.
- Поточний session-csharp.jsonl і каталоги speed-probe / coverage-audit у `%LOCALAPPDATA%/Pixora`.
- Версію, режим, зображення, кількість операцій, фактичний час і видимі дефекти.

У журналі `start.delayTransport` показує доступний таймер. `motion_group.inputCosts` містить заданий і фактичний час очікувань, кількість перевірок та час SendInput. `SafetySeconds` частково входить в `ActualWaitSeconds`: ці величини не можна просто складати. Вони допоможуть відрізнити затримки очікування від інших витрат.

Новий точний таймер перевіряється локально; прискорення й повне покриття у Rust потребують цього живого тесту.
