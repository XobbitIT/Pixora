# Pixora beta.56 — проблеми, виправлення та невирішені обмеження

Стан на 11 жовтня 2026 року. Джерела: журнали двох пристроїв, надіслані зображення та відео, історія виправлень і поточний код. Це перелік відомих проблем, а не гарантія відсутності інших дефектів.

«Виправлено в коді» означає реалізацію та офлайн-перевірки. Воно не означає, що всі пристрої вже пройшли живий тест. Для beta.56 пройшли 435 Core і 160 WPF перевірок; Release має 0 warnings / 0 errors. Новий живий прогін beta.56 не виконувався.

## Що залишається зараз

| Проблема | Підтвердження та поточний стан |
| --- | --- |
| **Сірі прогалини й неповна заливка** | На FCB видно незамальовані ділянки. У моделі надісланих налаштувань для 182885 із 613872 цільових px немає безпечних команд; на BVB — для 172967. Це реальне обмеження плану. Beta.56 не закриває його небезпечним виходом пензля за межі кольору. |
| **Adaptive не завжди швидший** | Великий Size може мати вузьке стабільне ядро. Тоді широкі проходи дають мало користі, а дрібні проходи потрібні для залишку. У beta.56 модель тризуба все ще оцінює Adaptive у 406,74 с проти 358,43 с звичайного режиму, але Adaptive покриває більше модельних px. |
| **Не всі повторні проходи зайві** | Beta.56 прибирає повністю надлишкові команди й скорочує вже покриті кінці за Solid-маскою. Часткове перекриття потрібне для суцільної заливки. Можливий або м'який край пензля не вважається гарантовано покритою ділянкою. |
| **Довге малювання** | Останній завершений BVB: 7856 операцій, 629,66 с активного часу. Видалення порожніх груп саме по собі не усуває тисячі потрібних малих штрихів. Складні 256-кольорові зображення залишаються дорогими. |
| **Занижений ETA** | Для BVB модель beta.55 давала 556,02 с, фактично було 629,66 с. У коротких планах початкова оцінка також нестабільна до накопичення вимірів. Живої перевірки ETA beta.56 ще немає. |
| **Кінцевий RGB палітри не повністю підтверджений** | 170 перевірок комірок палітри успішні, але перевіряли ціль перед кліком, а не колір фарби на полотні. Створення сторонніх HEX-кольорів у цих Palette-запусках не виявлено. Візуальну невідповідність кінцевих кольорів ще потрібно перевірити. |
| **Аудит іноді не може визначити результат** | Низькоконтрастний білий дає багато Unknown. Це не доведений пропуск і не підтверджене покриття. Не всі завершені запуски мали аудит. 100% у прогресі означає завершення команд. |
| **Size 1 і деякі форми не мають надійного ядра** | Читання значення 1.00 не доводить стабільний фізичний відбиток. Були слабкий контраст і малий перетин трьох масок. Size 3 — звичайний дефолт; Size 1 доступний за власного підтвердження. Це не доказ, що Rust взагалі не здатний малювати таким Size. |
| **Калібрування залежить від контексту** | Clipboard, фокус, положення полів, DPI, захоплення кадрів і стан Rust можуть впливати на перевірки. Додані альтернативне візуальне підтвердження та бюджети очікування, але універсальну надійність на всіх машинах ще не доведено. Слабке обладнання саме по собі не встановлене як єдина причина HEX-збоїв. |
| **Speed Probe може не підтвердити прискорення** | Потрібні незалежні повільні контролі, повтори та запас. Окремому Size може бракувати чистого місця; інший може не пройти критерії. Груповий запуск beta.56 полегшує організацію, але не скасовує ці вимоги. |
| **Виміри не переносяться довільно між пристроями** | Зміна геометрії Rust, DPI, розкладки або режиму кольору може зробити профіль застарілим. Старий профіль не має автоматично давати право на швидкий ввід. Після зміни ідентичності плану потрібен новий START. |
| **Локалізація не повна в розширеній діагностиці** | Основний інтерфейс має сім мов. Частина технічних пояснень для польської, німецької, французької, іспанської та російської ще використовує англійський fallback. |
| **Залишається складність UI та підтримки** | Значна частина WPF-інтерфейсу будується імперативно, а BuildUi перебудовує дерево під час окремих змін. Тести захищають від відомих розсинхронізацій, але всі розміри вікон, довгі переклади та живі послідовності дій ще потребують ручної перевірки. |

## Що саме змінює beta.56

- Пропускає порожні кольорові групи.
- Прибирає штрихи, повністю покриті попередніми Solid-штрихами того самого кольору, та скорочує покриті кінці.
- Зберігає початкову модельну маску покриття; відхиляє оптимізацію, якщо повний розклад стає дорожчим.
- Додає групову перевірку швидкості для кількох Size та окреме збереження результатів.
- Показує нове й повторне покриття кожного Size.

Для локального тризуба 6851 → 5378 штрихів зі збігом хешу маски. Це підтверджений офлайн-результат. Реальний виграш часу й вигляд фарби в Rust ще невідомі.

Контраст 80, RGB tolerance 12, перетин трьох відбитків, критерії Speed Probe й аудит не послаблені. Старий checkpoint потребує нового START через зміну ідентичності плану.

## Порядок наступної роботи

1. Фізичне покриття: зіставити карту модельних пропусків із завершеним малюнком; відокремити обмеження плану від втраченого вводу.
2. Кольори: перевірити фактичну фарбу після вибору палітри/HEX, а не лише цільову комірку.
3. Швидкість: порівняти звичайний та Adaptive на однакових зображеннях із записом покриття, команд і реального часу.
4. ETA: порівняти прогноз із тривалістю цих завершених запусків.
5. Надійність: пройти групові перевірки, часткову відмову, скасування та зміну контексту на різних пристроях.
6. Поліровка: завершити переклад технічної діагностики й перевірити розкладки різних DPI/мов.
