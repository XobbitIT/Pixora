# Pixora Target 1 — незалежність цілі від виконання

Дата: 19.10.2026. База: `1.0.14-rc.8+local-standard-guard-3`.
Збірка: `1.0.14-rc.8+local-target-1`. Виконано лише **завдання 1** з останніх вказівок користувача.

## Що змінено

1. `ImageRecipe` зберігає окремий знімок параметрів зображення: розмір сітки, fit/crop, кольорову палітру й ліміт, alpha, dithering, preblur, очищення та edge merge. Збережені значення і відсутні значення з тим самим дефолтом мають однакове представлення. Копія JSON не може змінити вже створений recipe.
2. `TargetPreparation.Build` отримує тільки source та recipe. Він виконує розміщення, фільтри, квантування й очищення та повертає RGBA, labels, палітру кольорів і TargetIdentity. Підготовка не отримує release/speed/input/adaptive settings, геометрію UI, координати палітрових кліків або профілі пензлів.
3. `Planner.Build` після підготовки приєднує координати палітри й будує штрихи. Для виконуваного палітрового плану перевірка відсутніх координат кліку збережена. Чистий image-stage може створювати ціль без цих координат.
4. Прибрано приховану залежність `EdgeRegionMerge.MinimumArea` від виміряного ядра пензля. Мінімум тепер одна клітинка цілі; явний параметр товщини збережено. Ревізія алгоритму оновлена. Edge merge залишається явною опцією, OFF за замовчуванням. Для старого налаштування ON з великим мінімальним ядром результат може змінитися — слід переглянути прев’ю. Вісім перевірених історичних планів цього ефекту не мали.
5. Пресети деталізації 2/3/5/8 px змінюють тільки клітинку. Пресет 5 px названо «Грубіше», щоб не подавати втрату деталей як прискорення вводу. Профіль руху доступний окремо у Standard та Experimental. Профіль чітких країв також зберігає обрану швидкість.
6. На сторінці підготовки показано розмір цілі, клітинку та ліміт кольорів, а також пояснення, що деталізація й кольори змінюють зображення. Довідку налаштувань оновлено; нові повідомлення локалізовано.
7. Допустимі числові ліміти кольорів 1–256 з конфігурації залишаються доступними у списку, навіть якщо відсутні серед готових варіантів. Наприклад, HEX=8 більше не замінюється на Auto під час читання форми після зміни швидкості.
8. Знімок image recipe додано до `command-plan.json.gz`, щоб наступний аналіз міг відділити підготовлену ціль від маршруту.

Справжня прозорість визначається alpha-каналом. RGB-шахівниця та чорний не видаляються автоматично. Наявне явне `fill_subject` збережено як параметр кадрування, не як визначення прозорості. Публічний Core підтримує клітинку 1 для внутрішніх image-reference тестів; інтерфейс і міграція налаштувань малювання зберігають мінімум 2.

## Перевірки та відтворення

- Core: **609 PASS**. Додано 6 регресійних випадків; один перевіряє 128 комбінацій Standard/Experimental × 4 швидкості × 2 рушії вводу × Adaptive ON/OFF × Palette/HEX × edge merge ON/OFF.
- WPF: **187 PASS**, включно з матрицею 84 DPI/layout. Новий тест перевіряє реальне редагування контролів у Standard/Experimental та Palette/HEX: швидкість не змінює recipe; пресет деталізації не змінює швидкість; пояснення клітинки/кольорів оновлюється.
- Фінальні збірки Core та App: **0 warnings / 0 errors**.
- Окремий `Matrix` replay: **256 комбінацій** із двома варіантами обробки (фільтри OFF та crop + preblur + median). Для кожного recipe байти RGBA, labels та TargetIdentity однакові в усіх режимах. **16 явних змін** cell/кольорів змінюють TargetIdentity, як і мають.
- Вісім збережених історичних планів порівняно з результатами Guard 3 на тих самих входах. Збіглися TargetIdentity, RGBA SHA, маршрути, кількість операцій, часові оцінки та послідовність заданих подій/очікувань замороженого емітера. TargetIdentity включає також байти labels. Базовий результат прив’язаний до SHA Core DLL Guard 3; новий — до SHA DLL цього пакета.
- У двох із восьми планів execution identity змінилась через нову ревізію edge merge, хоча target і маршрут збіглися. Старий checkpoint з іншою identity не переноситься автоматично; незавершений малюнок слід продовжувати попередньою збіркою.
- Контрасти, RGB12, guards, emitter та його очікування не змінювались. Штучні тести виконувались з вимкненим native input.

Відтворення з кореня доказового ZIP: зібрати `Source/tests/CanvasForge.Core.Tests` та `Source/tests/CanvasForge.App.Tests` через `dotnet build -c Release -m:1 -nr:false -p:SourceRevisionId=local-target-1`, потім запустити відповідні DLL. Для WPF потрібна Windows; TEMP/TMP мають бути доступними для запису. Replay має параметр `CorePath`; Matrix — такий самий параметр. Після збірки запустити Replay з `Replay/Inputs` та шляхом вихідного JSON, а Matrix — з каталогом результатів. Додано точні початкові входи, код harness, старий/новий JSON, PNG прев’ю, журнали й контрольні суми. `Comparison_Verify.py` перевіряє збережені та повторно створені результати.

Проміжні невдачі не приховано. Перша App-збірка зі спробою мережевого NuGet audit отримала NU1900 через недоступність nuget.org; фінальна збірка використовувала відновлені локальні залежності й однопроцесний MSBuild. Перевірка вразливостей пакетів не виконана. Перший повний WPF-прогін мав один застарілий тест, який вимагав одночасної зміни деталізації та швидкості. Його замінено перевіркою нового контракту зі збереженням швидкості; виконано повний повтор. Окрема рання UI-перевірка виявила відмінність missing/false у recipe JSON — дефолти тепер записуються явно.

## Новий живий матеріал від користувача

Відео `RUST 2026.10.19 - 14.58.45.01.mp4`, журнали та два останні каталоги запусків збережено окремим знімком. SHA відео та файлів — у `Intake/Intake.json` і `Intake/Files_SHA256.json`. Відео не включене до цього ZIP; в Intake зафіксовано його початковий шлях і SHA.

Для запуску `20261019-115850-7005d242733740198afcbe323aba823d` журнал Guard 3 повідомляє `completed`, 88/88 операцій, Active **34,0626757 с**, Wall **40,3153761 с**, Pause **0 с**. Переглянуто один кадр на 40-й секунді. Це приймання матеріалу та факт завершення вводу попередньої збірки, не оцінка фізичної точності нової версії. Детальний аналіз геометрії належить наступному завданню 2.

## Межі і порядок подальшої роботи

Нових живих тестів для завдання 1 не потрібно. Наступне завдання — офлайн-вимірювання H/V меж за наявними native before/after та зіставлення двох наборів даних. Виміряної корекції положення/товщини в цьому оновленні немає. У Rust нічого не запускалося агентом. Коміт і push не виконано; сукупні незакомічені зміни попередніх ітерацій збережені.

## що НЕ доведено

- Не доведено, що Standard малює фізично рівно або піксельно збігається з preview. Ця ітерація відділяє ціль від виконання; фізику сліду вона не виправляє.
- Не виміряно і не заявлено прискорення в Rust, точність ETA чи готовність Adaptive.
- Не підтверджені гіпотези про анізотропію та масштаб із відгуку; їх аналіз не входив у завдання 1.
- Матриця й replay — офлайн-докази, не live qualification. `inGameTest=false`, `physicalQualityCertified=false` для цієї збірки.
- Збіг восьми історичних планів не доводить незмінність усіх можливих старих конфігурацій, особливо edge_merge=ON із залежним від великого ядра мінімумом.
