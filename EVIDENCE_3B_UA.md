# Pixora Standard Evidence 3b — правки сценарію та Завдання 4–5

19.10.2026 · `1.0.14-rc.8+local-evidence-3b`. Пріоритет: точність, стабільність, швидкість. Живого вводу в Rust не виконано; Git commit/push не виконано. Попередні архіви Evidence 3 збережено.

## Результат

Внесено обидві правки з відгуку Qoder: додано чотири проби поточного пакетного Standard та явно названо бюджет тривалості. Офлайн завершено аналіз старого відхилення курсора; його джерело залишається UNKNOWN. Реалізовано чесні причини неготовності START та актуальний незалежний `run.json`.

Нових живих даних Evidence 3 поки немає. Офлайн-аналіз фізичного сліду виконується після отримання повного або перерваного користувацького збору. Запуск великого малюнка не потрібен.

## Уточнений протокол збору

- Перші 38 проб збережено з тими самими координатами й ID: 36 H/V, прямий/зворотний напрямок, 16/64/400 px, три блоки; дві 400-px смуги з 72 чорних і 16 білих проходів кожна. Кадри чорної та білої фази зберігаються окремо.
- Додано ID 38–41: дві H і дві V лінії по 400 px на окремих чистих ділянках. Використовується незмінний поточний preset `Max Speed` і той самий dense-емітер, що у звичайному Standard. Повний пакет — 48 послідовних фізичних точок: `Pitch3 × Batch16`. Pitch тут задає розмір пакета, а не пропуск двох пікселів між командами.
- Усього **42 проби, 44 колірні фази, 216 штрихів та 132 виклики native capture**. Копії фінального PNG проби не рахуються як новий native capture. Резерви рознесені, залишаються в межах мінімального Canvas 900×920 з запасом 10 px. Автоматичного Undo немає.
- Кожна проба заморожує свій `SpeedProfile`. Після одного пакета виконується одне реальне зчитування курсора; `IssuedPoints` містить надіслані команди, `Cursor` — фактичне читання. Курсорні спостереження всередині пакетів не вигадуються. Граничні перевірки маршруту й endpoint збережено.
- Новий protocol revision `standard-evidence-series-v3b` має новий hash. Попередню спробу v3 не можна видати за v3b або продовжити. `attempted.json` також блокує повтор після помилки підготовки до входу в основний runner; такий збій більше не залишає статус NOT_STARTED.

## Тривалість і публікація стану

Планувальний бюджет — **5–15 хвилин**, обмеження спроби — **20 хвилин**. Це не виміряний live ETA. У `duration-budget.json` записується точна сума запитаних очікувань емітера для заморожених налаштувань. При frame 20 ms і cycle delay не вище 20 ms вона становить **40,7496 с**. Решта — перевірки редактора/кольорів, стабілізація знімків, guard/cursor/API та файлові витрати. Оцінка 25–45 хвилин із відгуку припускала очікування кадру на кожну точку; поточний код цього не робить.

На першому focused fake-прогоні цієї ітерації повторилась `UnauthorizedAccessException`: тепер stack точно вказує на `File.Move(tmp, series-status.json, true)`, а не на малювання. Відмова збережена як INCOMPLETE: 36 проб / 37 фаз / 114 штрихів; native input був вимкнений. Першопричина того, хто відкривав/блокував файл, не встановлена.

Публікація статусу тепер допускає лише **до п'яти повторів перейменування метаданих із паузою 10 мс**, між штрихами, коли кнопка фарби відпущена. Append-only подія записана перед публікацією. Постійна відмова лишається помилкою; фарба, вибір кольору, проби та серія ніколи не повторюються автоматично. Успішний ввід звичайного Standard і його очікування не змінювалися. Окремий файловий тест утримує реальний read-handle: короткий lock відпускається, постійний завершується видимою відмовою без пошкодження старого стану.

## Завдання 4: що встановлено офлайн

Інцидент 18.10 о 23:04:39 належить збірці `local-standard-motion-2`, а не новому Guard 3. Відхилення виявлено після вертикального штриха Group 3 / Line 114, завершено 282/324. Expected `(1028,1148)`, actual `(1107,800)`. Actual відсутній у всіх 324 сегментах плану; останні UI-дії були приблизно за 14 секунд і мали інші координати.

Фаза endpoint після mouse-up виведена з архівного коду; в самій події поля phase немає. Одночасних foreground PID/title та повного cursor path немає. Тому причина **UNKNOWN**, а `(+79,−348)` — різниця двох точок, не виміряна траєкторія. Окремий `Pixora_Cursor_Jump_4_Report_UA.md` містить точні рядки журналу, перевірені SHA та межі висновку. Нового guard або поправки координат за цим інцидентом не додано.

## Завдання 5: START і run.json

START та підготовка використовують спільну пасивну перевірку збереженого стану. Показуються конкретні причини: Canvas, Size-track/числове поле, результат перевірки Size, застарілий/відсутній editor proof, зміна rect/DPI/геометрії. Busy/loading/paused стани також пояснено. Застарілий текст HEX про повзунки замінено на поле HEX та Size.

На прийнятому START створюється новий діагностичний запис `planning` ще до побудови плану. Той самий directory переходить до Painter. Перед countdown зберігаються актуальні лічильники, при F6 — `paused`, причина, реальний завершений прогрес і час. Рання помилка/скасування, зокрема до запуску clock, пише terminal-стан. `startedUtc`, `stateChangedUtc`, `updatedUtc`, sequence та scope розрізняються. Checkpoint і право на його перезапис цим журналом не змінюються.

Це не підтверджує живий стан редактора: runtime-перевірки перед вводом збережено. Розбиття руху/API/guard-часу залишається Завданням 7. Деталі й тести — в окремому `Pixora_Start_State_5_Report_UA.md`.

## Перевірка

- **615 Core / 198 WPF cases PASS**, включно з 84-layout DPI-матрицею; Core та App build — 0 warnings / 0 errors. Аудит мережевих NuGet-вразливостей у цій офлайн-перевірці не виконувався.
- Повний записувальний fake: **42/44/216**, усі216 gzip-трас, окремі кадри чорного/білого. NativeInput=false. Утримувані кнопки відпускаються на відмовах; часткові дані лишаються. Системний F6 у тесті не натискається: використовується спільний обробник із контрольованим рівнем клавіші й годинником.
- Нові bridge-тести перевіряють 48 точок у повному пакеті, 401 надіслану позицію на 400 px штрих, 10 пакетів разом із початковим переміщенням, без вигаданих per-point читань у пакеті. Додано перевірки причин START, початкового/paused/terminal журналу й файлової публікації.
- Replay 8 історичних планів проти Target1: target, identities, команди, очікування та заморожені події емітера збігаються. Цей replay перевіряє план, а не фізичну фарбу Rust.

## Після одного живого збору

Спочатку перевіряємо hashes, повноту подій/кадрів/трас та контекст кожної проби. INCOMPLETE не перетворюється на PASS або пропущений зразок.

Потім окремо для H/V, напрямків, довжин, позицій і профілів: залишок контуру від прямої, SD/P95/max, автокореляція, envelope товщини; фактичний курсор проти команд лише у записаних фазах. Чорні/білі смуги порівнюються на кадрах між кольорами, включно з правим обривом. Будь-який поріг сегментації зображення буде позначений як аналітичний, не як заміна RGB12/contrast80.

Чотири production bridge-проби зв'язують збір із поточним packet-шаблоном. Вони не ізолюють старий v1/крок3 і не дають підстав для універсальної mapping-корекції: позиції різні, обсяг малий, інструментація додає витрати. Так само 407 додаткових фіолетових клітин тризуба вже існували в target: рецепт Auto-палітри тут не змінено й автоматичного видалення відтінків не додано.

## що НЕ доведено

Фізична рівність Standard, першопричина хвилястості, причетність конкретного процесу до зміщення курсора, живий успіх нового збирача та його фактична тривалість. Не доведена продуктивність Max Speed, безперервний cursor path усередині пакета, готовність mapping/Adaptive, B0-шум чи незалежна held-out сертифікація. RGB12/contrast80 та геометричні пороги не послаблено; нові коефіцієнти у продукт не внесено.
