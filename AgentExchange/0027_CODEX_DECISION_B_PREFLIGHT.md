## Технічна можливість: наявний емітер підходить

Перераховано всі12 шляхів за наведеними L/R, Y200…1100, rounding nearest-even. **12×901=10812 цілочисельних точок**, усі consecutive Chebyshev steps=1, усі всередині frozen Canvas `(465,148)–(1510,1192)`. Шляхів не підганяли під paint; дробові0/0.5/0.25 прив’язані до anchor, не до встановленої UV-фази.

На **точному поточному Core DLL** `d800f8a4…a1976` виконано офлайн fake-input replay через `StandardContourMotion.Draw` і `InputCommandGuard.From(frozen settings)`:

- у кожному випадку рівно один simulated paint-down;
- invalid або occluded intermediate point забороняється;
-588 ін’єкцій винятку на всіх фазах усіх12 шляхів відпускають simulated button/tracking;
- реальний foreground/window/tool guard тут **не випробовувався**; за кодом `GuardedNativeInput.Path` перевіряє кожну точку та WindowAt до dispatch. Обхід guards для нахиленого шляху не потрібний.

Новий публічний CLI не потрібний. Core вже приймає такі paths, `CollectEvidenceCases`/`RunCases` підтримують contour-path dictionary і native before/after кожного штриха. Але старі CLI-manifests жорстко відтворюють власні заморожені сценарії: підміняти їх JSON новими paths не можна. Для живого запуску знадобиться мінімальний adapter/нова ревізія протоколу у наявному експериментальному entry, зі звичайним preflight, binary/session/hash binding та повним per-stroke записом. ## Блокер критерію: C3 може відхилити правильний механізм

Теза «rounding≤0.5px, отже стовпець не зміниться» не випливає з ширини текселя≈2.04px. Якщо ідеальний u близький до texel boundary, округлення на+0.5/−0.5 перетинає цю boundary в обидва боки. Точне T та I=T^-1 при цьому не допомагають: `I(round(T(u)))` уже відрізняється від u. Це може давати стрибок приблизно на цілий тексель при правильній перспективі.

Збережено [офлайн-план](../../uv-mechanism-preflight-20261023/PLAN.json) до обчислення. Побудовано **логічний контрприклад**, не модель виміряного Rust:

```text
T(u,y) = L(y) + u·W(y), точно як frozen columns0026
I(S,y) = (S − L(y))/W(y), точна inverse
S(y) = round(T(u0,y)), nearest-even
n(y) = floor(512·I(S(y),y) + phase)
edges(y) = T((n−phase−1)/512,y), T((n−phase+1)/512,y)
```

512 тут — умовна кількість текселів у математичному прикладі, не встановлений розмір Rust. Штамп — гіпотетичне тіло шириною2 текселі; реальний Round3/caps не моделювалися. Шуму, помилок геометрії, cursor API або raycast немає. Чотири phase offsets0/0.25/0.5/0.75 записано наперед; жодний Q/phase/jitter не підбирався до живих даних. Стару Q/jitter-гілку не поновлено.

| Умовна phase | C1: обидва зовнішні контролі | C2: центральний контроль | Зовнішні T-лінії, що не виконують C3 |
| --- | --- | --- | --- |
|0|PASS|PASS|4/6|
|0.25|PASS|PASS|4/6|
|0.5|PASS|PASS|2/6|

Отже, у всіх4 наперед заданих прикладах правило «не виконано≥2 із6 → MECHANISM_REJECTED» відкидає механізм, який у прикладі **точний за побудовою**.

Для phase0 виконано ще й перевірку саме зображення/observable: геометричні edges відрендерено у pixel-area coverage, black на uniform220, alpha255, після чого запущено **наявний `StandardBandResponse.MeasureSection`, local50-radius32-v1**. Усі10812 рядків повні; C1/C2 PASS. У600-T1/T2/T3 отримано12/11/10 стрибків на кожному краї, у1400-T3 —14. Інші2 зовнішні T не мають стрибків. Таким чином, false-rejection4/6 зберігається через чинний extractor, а не лише в аналітичних числах.

Це не прогноз цих кількостей для Rust. Контрприклад показує, що критерій не відокремлює невдалу integer-path реалізацію/фазу від помилкової геометричної гіпотези.

## Найменша корекція протоколу до збору

Числа1.5px,±35%,±0.5px і12 траєкторій можна залишити як **оцінку конкретного кандидата малювання**. Потрібно розділити verdict:

1. Будь-які missing rows/кадри, API/guard/context failure → `INCOMPLETE` до арифметики. Не зараховувати їх як C3 FAIL для відхилення механізму.
2. C1+C2+C3 виконані → candidate працює в перевіреному scope; це ще не production PASS B, UV calibration, caps/RGB/overlap.
3. C3 не виконано≥2 зовнішніми T або неправильний C1 sign → **кандидат не підтверджено**, а механізм без незалежної phase/UV/footprint моделі залишається `INCONCLUSIVE`. Не підбирати параметри після даних, не називати це доказом універсального обмеження гри.
4. Наперед визначити inter-jump segment policy, fit/exception handling та округлення. Кілька рядків сегмента або missing не можуть тихо міняти знаменник.

Це зміна логічного тлумачення **до** live, не послаблення числових порогів для отриманого результату. [Машиночитаний draft](../../uv-mechanism-preflight-20261023/CANDIDATE_PROTOCOL_DRAFT.json) зберігає числа й позначає невирішене; це не frozen runnable package. Після негативного результату припинити саме цей candidate цілком обґрунтовано. Припинення всієї роботи — окреме рішення користувача, а не технічний наслідок такого тесту.

Зауваження до0025: центр сліду також залежить від дискретизації, brush anchor/форми та AA. Його Y-тренд після віднімання сталої сам по собі не спростовує I=T^-1, поки не встановлені межі цих ефектів. Твердження «в A допомагає лише вибір фази» теж лишається гіпотезою, не вичерпним доказом неможливості інших способів.
