## Нові зауваження

1. **Повноту можна підробити через `with`.** `StandardPhysicalLineMetrics` — публічний record з публічним конструктором. `line with { MissingAlong = [], ObservedSections = …, ObservedAdjacentPairs = … }` робить неповну лінію `Complete`, а контекст-ID перевіряє лише target+provenance, не самі значення. Тести перевіряють підміну provenance, але не цієї. Якщо wrapper має бути межею довіри — зробити конструктор internal / фабрику лише через `MeasureLine`, або включити в контекст хеш вхідних перерізів (тоді `SourceEvidence` логічно входить у результат, не в контекст). Якщо межею довіри він не є — записати це в контракті.
2. **Як переводити похибку краю в похибку метрики.** Ви правильно заборонили переносити бюджет одного краю. Готове правило для дослідження U: якщо кожен край кожного рядка відомий з точністю ±e (sup-норма), то похибка метрики не перевищує k·e, де k = 1 для max двох країв, P95 pooled і P95 по рядках (порядкові статистики 1-ліпшицеві); k = 2 для розмаху краю, похибки ширини й сусідньої сходинки; k = 4 для розмаху ширини. Межа консервативна (спільний зсув усіх рядків у розмахах і сходинках скорочується).
3. **Кінці не мають аналогічної прив'язки.** Для caps немає provenance/контексту, а єдина невизначеність — геометрична дискретизація контуру; похибки захоплення й виділення контуру не враховано. Порівняння caps через `CompareMetric` зараз може дати WithinLimit без цього. Потрібен такий самий wrapper, як для ліній, або явна заборона рішень по caps до нього.
4. Дрібне: «сума» трьох компонент — консервативна (лінійна), не квадратурна; добре, але записати в контракті, щоб ніхто згодом «не уточнив» до √Σ² без доказу незалежності.
