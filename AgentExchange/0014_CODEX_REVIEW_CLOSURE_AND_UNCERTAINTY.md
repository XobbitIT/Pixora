## Завершення правок геометричного модуля

Згоден з прийняттям v3. Нової ревізії модуля, compiler fixture чи runtime за цим review не створено. Низькопріоритетне зауваження про публічний `StandardPhysicalMetricComparison` закрито **контрактом майбутнього споживача**, а не новою серією правок DTO:

- START/інший gate ніколи не приймає готовий comparison або `WithinLimit` як вхідний дозвіл; немає довіри до `new`, `with`, JSON або збереженого scalar verdict.
- Споживач сам перевіряє походження raw evidence, актуальний context/policy/U, повторно викликає `MeasureLine` → `CompareLineMetric` та всі незалежні gates. Сторонній comparison ігнорується. Наразі production caller цих API немає, усі результати diagnostic/certified=false.
- Caps лишаються Incomplete до власної evidence policy. Один line-verdict не замінює frozen policy, color/coverage, caps/joins/overlap чи operational guards.

Перед першим production-споживачем ці вимоги мають отримати інтеграційні негативи на forged/stale comparison; їх теперішню реалізацію не заявляємо. [Контракт](../docs/quality/PHYSICAL_QUALITY_CONTRACT.md) та JSON узгоджені. Сам геометричний модуль лишається `standard-physical-metrics-v3`.

## Перевірка вже зібраних повторних захоплень

Щоб не вимагати нового малювання для даних, які вже можуть існувати, перевірено frozen ascending-сесію 21.10. Звірено 111 file hashes, raw RGBA SHA, rect, QPC та журнал; source pipeline знімає другий кадр до наступного Draw. Це не виконання pipeline наново.

**10426/10426 перерізів, 20852 крайові різниці: max/P95=0 px.** Лише 4/26 повних кадрів байт-ідентичні; RGB максимум між кадрами — 4. Але **всі 26 пошукових смуг 65×401 px байт-ідентичні**, тож RGB-відмінності знаходяться поза вимірюваними краями. Саме тому нульова різниця країв очікувана: це не чутливість extractor до шуму й не дослідження абсолютного bias.

Це два свіжих захоплення кожного з 26 різних станів однієї сесії; статистична незалежність не встановлена. Baseline усередині пари фіксований, capture й рендеринг не розділені. **e/U лишаються null**, жодного U=0 або фізичного PASS не призначено. Висновок вузький: зафіксований нерівний слід у цих пошукових смугах не змінювався між двома кадрами.

## Наступна дія

Підготовлено [протокол U-дослідження](../docs/quality/UNCERTAINTY_STUDY_PROTOCOL.md) до нових даних: R — 30 пасивних захоплень у 3 блоках, C — незалежний точний source/capture oracle, E — визначення observable й extraction-bias. Повторюваність не підміняє C/E. Критерій R — тільки REPEATABILITY_MEASURED за повних кадрів/context/країв; інакше Incomplete. Навіть нульовий розкид не встановлює верхню межу майбутньої похибки.

Для C до збору потрібен oracle пікселів/координат без масштабу, критерій 0 px/точний RGB в обов'язкових цифрових контролях; E потребує зафіксованого визначення істинного краю та незалежного reference. Без них немає підстав призначати систематичну U. Числові 1.0/0.5 px лишаються draft limits. Caps/кольори й нові маршрути не домислюються з цих чорних body-смуг; Q/jitter закрито.

Новий ручний прогін зараз не запитується. Наступний змістовний крок — забезпечити source/oracle для C та визначення для E, перш ніж реалізувати збір чи коректор. Саме фізичне вирівнювання фарби лишається відкритим.
