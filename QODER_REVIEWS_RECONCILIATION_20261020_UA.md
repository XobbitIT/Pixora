# Узгодження рецензій Qoder: Size3 Repeat1 і State Timing6–7

20.10.2026. У цьому етапі прочитано вкладену Size3-рецензію й State Timing-рецензію з повідомлення користувача. Виконано додаткову перевірку 97 native RGBA-кадрів та читання конкретних файлів коду. Новий живий тест, збірка, native input або зміна алгоритму продукту не виконувалися.

## Size3: прийняті уточнення та нові докази

Первинний Live Report і Evidence ZIP `79f631ae…a36ef` залишені незмінними. Випущено окремий `Report_v2_UA.md`.

1. Межі висновку вказані вже в першому абзаці: Round3 / Size3 / Max Speed / identity, один Canvas 1045×1044 / DPI 96. Це не сертифікація чи спростування всіх режимів Standard.
2. First→second та first→third: первинний пакет зберігав суми, а не списки координат. Тепер `Pixel_Coordinate_Check.json` зберігає 79 точних координат і RGB трьох кадрів. Набори координат справді однакові: symmetric difference 0 у всіх 32 пробах. Це нове доповнення після review, не доказ, який був у первинному пакеті.
3. Для зламів треба розрізняти геометрію й зміни пікселів. На центральних ділянках 12/19/27 немає змін>12 між first→second/third. Для 18 є один піксель `(1267,393)`: `[43,24,13]→[19,0,0]→[19,0,0]`, delta 24, саме на рядку зламу. Геометричний злам уже є в першому нанесенні, а residual18 змінюється 1.103541→1.102843. Фраза «жоден піксель зламу не змінюється» була б хибною; у v2 виняток названо прямо.
4. After-third→final — окреме порівняння. Максимальна delta в усіх32 reservations дорівнює1; у second→third максимум також 1 і 0 пікселів>12. Це не byte-identical кадри.
5. Freeze-before-heldout у поточному пакеті є процедурним твердженням реалізації, самозаписаним receipt та нашим фокусним тестом. Незалежної зовнішньої хронології I/O немає. Попереднє копіювання/хешування всього набору вже відкривало байти held-out файлів; receipt стосується порядку decode/analysis у C#-аналізаторі, а не всіх OS opens. Історичний незалежний audit заднім числом не створюємо.
6. `D:/Pixora` локально перевірив Codex під час аналізу. Qoder перевіряв runtime ZIP та Source_Binaries. Ці два рівні перевірки не змішуємо.
7. Початкову відмову доповнено виміром `canvas-frame` 6/16 при required 15, з повним збігом трьох інших перелічених груп. Зміна config rect між спробами не встановлює сама по собі хибність detector.
8. Названо набір довгих V без великого зламу: 3/7/11/31, включно з held-out 31. Для 8349 вказано точне походження: сума `RequestedRgbPixels`.

Сам факт зламів/перезапису меж підтверджений двома способами вимірювання на тих самих даних. За описом Qoder його decoder дав інші абсолютні residuals; код decoder не наданий, ми його не запускали. Це підтримує стійкість висновку, але не тотожність чисел або нову живу кваліфікацію.

## State Timing6–7: два виправлення до формулювань рецензії

**Finish не входить у Service в новому контракті.** У доставленому коді та UI це окремі поля:

`Colors + Motion + Service + Finish + Pause + Countdown = Wall`

`Active = Wall − Pause − Countdown`

Тобто Finish входить до Active, але не до Service. Це безпосередньо видно в RunTimeBreakdown.Read/Accumulate, timingContract у PaintRunSnapshot і рядку UI TimingProgress, який друкує Service та Finish окремо. Хеші цих поточних файлів збігаються з Source Receipt саме збірки 6–7; уточнення не є пізнішою підміною реалізації.

**765/765 належать Source/Evidence-пакету.** Runtime ZIP містить 257 файлів: 256 payload entries у Files_SHA256 плюс сам manifest. Source/Evidence ZIP містить 766 файлів: 765 payload entries плюс manifest. Загальні розміри/SHA з рецензії відповідають Receipt; у цій додатковій перевірці прочитано структуру zip і кількість entries, а не проголошено нове незалежне виконання всіх тестів.

Конкурентний fixture вже перевіряє двох власників через Parallel.ForEach і рівно один успішний commit. Lease fixture утримує FileShare.None handle в тому самому процесі. Його назва згадує cross-process lease, але це не випробування двох окремих writer-процесів і не crash/kill recovery. Цей непокритий сценарій залишається в черзі окремих офлайн-тестів. Звичайний UI має single-instance lease, тому два відкриті GUI не слід вважати єдиним способом перевірки concurrency.

Для Size3 wall 512.391624 с межі задані подіями series_started→series_finished: початковий countdown і PrepareBrushCalibration перед runner до цього інтервалу не входять; baseline, capture, вибір фарби, перевірки й metadata/file I/O всередині серії входять. Слово «підготовка» без цих меж двозначне. Вкладені trace/capture/requested waits не додаємо як незалежні фази.

## Порядок наступної роботи лишається цільовим

1. Офлайн зіставити місця зламів із виданими пакетами, напрямком і позицією; не оголошувати доведеною ані конкретну Rust-проєкцію, ані весь внутрішній шлях ОС.
2. Розділити причини відмов профілю: source, rendered RGB, repeat stability, position/generalization, Possible-envelope. RGB12/contrast80 не послаблювати, медіану не призначати новим очікуваним кольором.
3. Перевіряти кандидатну модель full-stroke і межі кольорів; gap6 не є універсальною поправкою. Одиночний профіль білого з цього набору не виміряно.
4. Уже переглянуті controls не називати untouched під час підбору нової моделі. Нові експерименти визначати після отримання конкретної офлайн-корекції, а не повторювати загальне малювання.

## що НЕ доведено

Конкретний механізм зламу; production-корекція; незалежний freeze-I/O audit; crash/kill release у двох writer-процесах; загальна фізична якість Standard/Adaptive. Доповнення документує й уточнює докази. Код продукту та пороги не змінювалися.
