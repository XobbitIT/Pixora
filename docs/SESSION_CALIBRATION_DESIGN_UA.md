## 2. Rapid проти Max Speed: що реально виміряно?

`SpeedProfile.All` (`Models.cs:464`): Rapid = pitch 1, batch 4, point delay .00035; Max Speed = pitch 3, batch 16, .0001. `StandardContourMotion.cs:17–21` видає **кожну** точку dense path без геометричного прорідження: пакети до 4 проти 48 точок, wait = delay×ceil(count/pitch). Повний пакет: 1.4 мс проти 1.6 мс, але 4 проти 48 точок. StartDelay .0015/.0005 обидва обмежені settle≥5 мс; UpDelay .0015/.001 обидва перекриті frame=20 мс; initial hold 20 мс, end hold≥20 мс, загальний down≥40 мс, release≥20 мс (`Models.cs:610–612`). Реальний час transport не дорівнює лише requested waits.

**Так, є тексельні live-дані з фактичним Max Speed.** Питання має дві різні відповіді:

- Для значення **settings.speed_profile не Rapid** успішного продуктового live-прогону в 0063–0105 не наведено; 0084:17, 0099:20–22 і 0100:24 прямо описують відмову основного Max Speed-конфігу та Rapid у пакеті.
- Для **фактичного emitter speed** продукт і пілоти вже використовують Max Speed: `Painter.TexelProduct.cs:35`, `StandardRepeatSeries.cs:16`; picture/plane/calib samples явно мають цей Speed (`StandardRowPicturePilot.cs:280`, `StandardPlanePilot.cs:66`, `StandardRowCalibPilot.cs:123`), runner передає sample.Speed (`Painter.EvidenceSeries.cs:234`). Frozen pic9 context також Max Speed (`tests/CanvasForge.App.Tests/Fixtures/RowPicture9/protocol-pic9.json:39`), profile — Max Speed. Живі результати 0096/0098, 0100/0103/0105 існують; це доказ фактичного Max Speed за цим шляхом, а не нового порівняльного досліду Rapid↔Max Speed. Первинні зовнішні raw-пакети тут не перевідтворено; висновок спирається на код, checked-in frozen protocol і наведені звіти.

Отже, для мінімального дизайну немає підстав перемикати emitter на Rapid або вимагати повторного speed-досліду лише через рядок settings. Слід явно відокремити requested speed від effective texel speed у session-record/інтерфейсі. Таймінги, guards і controls основного effective-конфігу все одно перевіряються окремо.
