# Модель відгуку Standard у UV: перегляд після живого пілота

Revision: `uv-response-observation-v1-draft`, 23.10.2026. Це уточнена робоча модель спостережень і вимог до наступного коректора. Вона **не є** реалізованим фізичним коректором, виробничим профілем або затвердженим числовим контрактом якості B.

Підстава: [аналіз живого пілота0033](../../AgentExchange/0033_CODEX_UV_LIVE_ANALYSIS.md), [перегляд моделі0034](../../AgentExchange/0034_CODEX_UV_MODEL_REVIEW.md). Заморожений дослід залишається INCOMPLETE через Y200; його протокол, критерії та golden не змінено.

## 1. Повний ланцюжок

```text
target у texture/UV
    → маршрут екранних команд c[j] + emitter/timing
    → фактичний рух курсора (записані readings — лише вибірки)
    → I_context: редакторське відображення команди в місце нанесення
    → E_context(history, path, size, shape, color, exposure): фарба
    → T_context: проєкція текстури + растеризація/фотометрія
    → native capture 1:1 у physical screen px
    → D_observable(before, after): два краї або явна відсутність виміру
```

`I`, `E`, `T` і спостережуваний `D` — різні частини. Навіть добра оцінка паперової рамки не визначає весь ланцюжок. Попередня формула `L(y)+u·(R(y)−L(y))` — screen-space proxy стовпця за паперовими межами; вона не є виміряним inverse input mapping і не встановлює справжні UV-границі чи роздільність текстури. Не вважати512 встановленою роздільністю.

Транспорт Windows продовжує працювати у physical screen px з identity mapping. Жоден емпіричний transform не застосовується до controls/HEX/palette/ROI або індексування native screenshot. User rect зберігається точно.

## 2. Вихід моделі — два краї та повнота

Для кожного вимірюваного екранного перерізу зберігати:

```text
screenY, low(screenY), high(screenY),
center = (low + high)/2,
width = high − low,
observableRevision, evidencePairHash, contextId,
valid / missing / ambiguous + reason
```

Немає припущення, що `low = center − constantRadius` і `high = center + constantRadius`. Місця/знаки/кількість переходів на двох краях можуть відрізнятися. Спільний зсув обох виміряних країв не змінює їхньої ширини; перенос такої маски не може бути доказом виправлення ширини.

Це властивість **моделі переносу записаної маски**, не межа можливостей нового реального штриха: зміна команди може змінити сам відгук, а не просто пересунути стару маску. Тому не прогнозувати невиміряний штрих формулою `oldEdge + commandDelta`.

`screenY` observed-перерізу не прирівнюється до моменту виконання команди з тим самим Y. До/після кадри не містять часової відповідності для кожної внутрішньої точки; близькість стрибка до command-X transition не доводить причинність.

## 3. Растеризація та observable — частина моделі

Одна геометрична зміна може бути видима в native capture протягом кількох рядків. Ідеальний стрибок2px дає дельту2px, а розподілений перехід `0→1→2` дає дві дельти1px. Незмінний детектор `|Δ|≥1.5` у другому випадку нічого не рахує. Тому кількість/сума таких подій характеризують визначений observable, а не автоматично кількість переходів тексельної ґратки.

Зберігати повні low/high перерізи, знакову й абсолютну зміну, ширину та перехідні ділянки. Сума S може скорочувати різнознакові події: мала S сама по собі не є рівністю. Не замінювати frozen C3′ новим об’єднанням переходів після отримання результатів.

Під час наступної перевірки будь-якого нового детектора/моделі потрібні окремо задані до кваліфікації приклади: різкі й розподілені переходи, різні фази семплювання, неоднакові переходи країв, зміна ширини, caps та missing rows. Це вимога покриття моделі, а не доведений фізичний kernel Rust. Коефіцієнти розмивання, масштаб ґратки та числові критерії не виводяться мовчки з цих12 ліній.

`native-band-local50-radius32-v1` залишається діагностикою. Local45/50/55 у перегляді — аналіз чутливості; формула порога `inside+f·(background−inside)` вказана явно. Не вибирати найсприятливіший f, не переносити це в RGB12/Solid. Пороги paint-контракту не послаблюються. Невідомий бюджет похибки лишається невідомим; threshold sweep не оцінює повну фізичну U.

## 4. Контекст та історія

Спостереження прив’язане до exact path і session/capture geometry, DPI, origin, canvas, shape/size, requested color, emitter revision, таймінгів, напрямку, стану до штриха та повної історії накладань. Фотометричний observable і метод вимірювання також версіонуються.

Таблиця з іншої сесії або іншого маршруту не стає виміряним результатом поточної комбінації. Не інтерполювати відсутні команди/повороти/overlap. Статична dot-маска не доводить рухомий Solid. Невідома комбінація → unavailable, без відсоткового припущення покриття.

Дванадцять UV-ліній уже використані для дослідження моделі; вони не є untouched held-out для нового підбору на цих же даних. Новий fit потребує окремого наперед визначеного незалежного контролю. У цьому перегляді fit/коефіцієнти не створювалися.

## 5. Body, caps і кінцева якість

Body і caps — окремі ролі та результати з наперед заданими координатами. Слабкий cap не може ретроспективно стати пропущеним body-рядком; відсутній mandatory sample означає INCOMPLETE. Нова політика не переписує Y200 старого досліду.

Для B потрібні перевірені texture/UV target geometry і числовий контракт: окремо положення двох країв, ширина, перехідні нерівності, caps, колір, стики/overlap та невизначеність. Екранна сходинка або її відсутність не є самостійною сертифікацією UV. `1screen px` не прирівнюється до `1texel`.

Приймання геометрії має спиратися на відхилення **повних** виміряних меж від заздалегідь визначеного target, з їхньою U, а не лише на кількість thresholded подій. Наявні `StandardPhysicalQuality` метрики можна використати після визначення сумісної геометрії/контексту й observable; саме перейменування screen-метрики на UV цього не забезпечує. C3′ event statistics зберігаються як окрема діагностика механізму.

## 6. Відповідність поточному коду

| Модуль | Що зберігається / чого не припускати |
| --- | --- |
| `StandardUvPilot` | Frozen12-path діагностика. Паперова формула не стає production mapping. |
| `StandardUvAnalysis` | Суворий старий missing/C3′ контракт відтворюється незмінно. Його adjacent-event лічильник не є універсальним фізичним детектором. |
| `StandardBandResponse` | Історія before/after, два виміряні краї, explicit missing. Local50 не є гарантованим контуром фарби. |
| `StandardBandContour` | Старий експеримент із перенесенням виміряних меж; його surrogate prediction не підтверджує реальний новий штрих. Не робити default. |
| `StandardDiscreteBand` | Уже розділяє low/high exact-command frontiers і лишає невідомі комбінації unavailable. Зберегти цю межу; різні overlap histories не видавати за підтверджений union. |
| `Painter` / guards | Зміни моделі не змінюють input safety, ROI16/0.985/delta0, release-on-error, settings або звичайний START. |

Перегляд0034 не перебудовував ці модулі або checkpoint/profile serialization. Наступний кандидат має прогнозувати обидва краї і ширину та пройти незалежну перевірку повного маршруту; самі уточнені назви або діагностична модель фізичний дефект не закривають.

## 7. Реалізована частина forward-моделі, 23.10.2026

[StandardStrokeObservation.cs](../../src/CanvasForge.Core/StandardStrokeObservation.cs) реалізує `standard-two-edge-observation-hypothesis-v1`: **задана геометрія двох країв → піксельне покриття → явно заданий sampling kernel уздовж штриха → незмінний local50**. Це не ідентифікація фізичних I/E/T за командами. Geometry/context/kernel/paint hypothesis подаються явно; автоматичних fit, phase selection, interpolation або коректора немає.

- Незалежні low/high, center/width, ролі Body/StartCap/EndCap. Наявний null/null section означає відоме нульове покриття; відсутній section — невідома геометрія. Відсутній сусід для kernel не доповнюється нулем чи екстраполяцією.
- Exact path/order, контекст старих collecting binaries/emitter, history, geometry hypothesis, kernel і before RGBA bound у IDs. Окремий prediction ID включає реалізацію нового Core. Ці hash — прив’язка заявлених даних, не самостійний доказ походження.
- Усі масиви й результати — власні immutable snapshots; повернення diagnostic raster копіює буфер. Растер змінюється тільки в потрібних рядках у cross±32; поза ним це before-кадр, не повний прогноз зображення і не Possible/Solid.
- Missing/ambiguous на будь-якому потрібному рядку → INCOMPLETE; aggregate maximum/width/center/RMS residuals лишаються null. Частковий P95/середній результат не легалізує неповний контур. Усі verdict/dispatch/Solid/eligibility прапорці залишаються false/0.
- `Compare` вимірює розбіжність **прогнозу й спостереження**, не фізичну похибку від прийнятого UV target. Він не видає WithinLimit чи quality PASS і не підставляє U=0.

13 сценаріїв у чинному Core host перевіряють різкі/розподілені переходи, H/V/reverse, ширину при правильному центрі, caps, missing/support, fragmented contrast, binding та snapshots. Тимчасовий офлайн-режим того самого test host зіставив усі8 старих pre-live геометричних гіпотез із sharp і явно гіпотетичним дворядковим kernel на12 native before-парах. Жодну фазу не обрано. [0035 — результати](../../AgentExchange/0035_CODEX_OBSERVATION_MODEL_IMPLEMENTATION.md).

Результат не дає дозволу на inverse-коректор: full200…1100 —192/192 INCOMPLETE; окремий post-run interior216…1084 —189 complete і3 incomplete, усі збережено. Для повних interior comparisons nominal max-edge residual1.285…5.727px; це невідповідність саме заданих гіпотез, без установленої U/UV budget. Фізичну нерівність Standard ще не виправлено.
